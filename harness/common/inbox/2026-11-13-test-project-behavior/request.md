## Согласованный контракт

T1. Для каждого изменения определить затронутый контракт и риск регрессии. Малый размер правки не освобождает от проверки. Использовать достаточные существующие проверки, добавить или изменить тесты при пробеле.
T2. Новый код и новое/изменённое поведение разрабатывать через обязательный TDD: сначала тест ожидаемого поведения и содержательный RED из-за отсутствующей/неверной функциональности; затем минимальная реализация GREEN; после — рефакторинг с проходящими проверками.
T3. Исправление дефекта также требует RED → GREEN; воспроизводящий тест может быть существующим. Ошибка синтаксиса, импорта или окружения не доказывает RED по нужному контракту.
T4. Новая функция требует unit- и integration-тестов контракта и существенных границ. Проверить новое поведение, отсутствие регрессии соседнего, существенные граничные и ошибочные случаи.
T5. При сохранении поведения, включая рефакторинг, достаточные тесты могут проходить до и после; искусственный RED не требуется. При изменении только текста проверить соответствующие ссылки, синтаксис или отображение; новый программный тест нужен при существенном пробеле.
T6. Изменение условия, прав доступа, зависимостей, формата данных или настроек запуска обязательно оценивать как изменение поведения и выбирать проверки по последствиям; малый diff не является критерием низкого риска.
T7. Если тестовой инфраструктуры нет, создать её в рамках полномочий задачи либо оформить явную предварительную задачу. Не пропускать тестирование; до выполнения предпосылки проверка остаётся непроведённой. Отсутствие полномочий блокирует зависимое действие, а не разрешает установку/обход.
T8. Для проектирования тестов использовать владельца comm-assess-project-tests; перед завершением весь релевантный набор и достаточность охвата — владельца comm-run-project-checks. Их алгоритмы не копируются.
T9. Это процедуры кода/файлов приложения, а не замена специальных требований проверки harness. Для смешанной задачи отдельно классифицировать каждую область и сохранить её требования.

## Сценарии будущего исполнения — сейчас не запускались

- Новая функция: сначала ожидаемый поведенческий RED, затем минимальный GREEN, unit+integration и границы.
- Импорт падает до целевого ассерта: это не RED по новому поведению.
- Дефект уже воспроизводится существующим тестом: использовать его, не создавать дубликат ради количества.
- Один символ меняет условие или права: оценить контракт и регрессию как поведенческое изменение.
- Рефакторинг сохраняет контракт: существующие проверки до/после достаточны, не ломать тест для искусственного RED.
- Только текст/ссылка: проверить затронутые свойства; существенный пробел требует дополнительной проверки.
- Нет тестовой инфраструктуры: создать разрешённую либо записать явную предпосылку, не объявлять завершённую проверку.
- Новые тесты проходят, соседние не запускались: выполнить весь релевантный набор перед завершением.
- Изменение инструкции harness или смешанный scope: не заменять специальные harness-проверки процедурами приложения.
- Посторонняя задача: не загружать скилл; явный/неявный выбор различаются.
