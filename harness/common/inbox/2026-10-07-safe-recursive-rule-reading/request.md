# Безопасное полное чтение правил

Дата создания: 2026-10-07.

## Контекст

Потребность возникла при полном аудите harness и повторном разборе пункта 2
2026-10-07. В трёх сохранённых сессиях Codex использовал
`.claude/rules/comm-*.md` или `.claude/rules/*.md` для cat. Такие glob не
выражают исключение README.human.md и пропускают вложенные либо личные правила.
Причина: запрет уже присутствует, но положительный способ полного чтения
не показан; существующая проверка проверяет только поиск по содержимому.

## Решение и разрешённый состав

Пользователь принял предложенные рекомендации, затем поручил создать заявку,
сделать коммит, выполнить её и сделать коммит результата.

1. Дополнить существующее правило коротким рецептом: отдельное перечисление
   всех машинных Markdown через rg с human-исключением и --no-ignore; затем
   отдельное чтение явно перечисленных путей с кавычками. Получить полный
   вывод до выбора скиллов. Полный кандидат: candidate/comm-human-folder-guides.md.
2. Расширить существующий check_human_guide_search.py сценарием чтения правил,
   сохранив прежнюю проверку поиска. Проверять common-only и combined.
3. Добавить минимальную проверку оракула; получить свежие результаты Codex,
   сохранить доказательства и учёт. Публикация source/native следует
   действующему gate; кандидата недостаточно для закрытия заявки.

Отдельный универсальный reader, новые зависимости и изменения AGENTS/CLAUDE
не требуются. Другие пункты аудита и чужие заявки в состав не входят.

## Наблюдаемый контракт

Сначала инструмент возвращает полный список правил без README.human.md.
Следующий вызов читает каждый машинный файл полностью, без glob, включая
вложенный файл, имя с пробелом, личное имя без comm-/proj- и игнорируемый файл.
Человеческие canary отсутствуют во всех событиях. Чтение закончено до скилла.
Проверка должна отвергать пропуск файла, совместное перечисление/чтение,
glob и обрезанный вывод. Старый сценарий поиска продолжает проходить.

RED: сохранённые три нарушения и падающая проверка нового оракула на старом
коде. GREEN: детерминированная проверка плюс свежие нативные сессии финального
кандидата в обоих режимах. Общие проверки и generic plugin-eval отдельно
от нативного поведения; результаты прошлой версии не объявляются текущими.
