# Разбор замечаний Plugin-eval после оценки скилла

Создано 2026-11-18.

## Причина

При проверке кандидата для production rollout Plugin-eval присвоил A (95), оставив предупреждение `description-trigger-weak`. Нативные проверки подтвердили загрузку, а вариант `Use when…` отдельно не сравнивали. Этот случай показывает, зачем оценивать применимость замечаний и пробовать исправления независимо от итоговой оценки. [Отчёт о проверке](../../testing/evidence/2026-11-18-execute-production-rollout/2026-11-18-report.md)

Действующий скилл `comm-validate-harness-instructions` уже требует разбирать результаты и повторять обязательные проверки. Предложение конкретизирует действия после отчёта Plugin-eval в [существующем условном ресурсе](../../skills/comm-validate-harness-instructions/references/evaluation.md). Для разбора сначала нужен отчёт, поэтому постоянно загруженное правило, само по себе или вместе со скиллом, здесь не требуется. [Полный кандидат с уточнением](candidate/comm-validate-harness-instructions/references/evaluation.md)

## Запрос пользователя

При проверке скилла разбери полный отчёт Plugin-eval, даже если он получил оценку A.

1. Исправь ошибки и выполни обязательные требования. Для каждого применимого предупреждения попробуй минимальную правку в рамках задачи. Например, при `description-trigger-weak` попробуй формулировку `Use when…`, сохранив все условия, при которых скилл должен загружаться.
2. После каждой правки сначала перезапусти быстрый Plugin-eval и сравни результаты. Если правка не помогла, верни рабочую формулировку и запиши, что попробовал и почему оставил замечание.
3. Если замечание касается покрытия исполняемого кода, проверь, можно ли получить артефакт из реального запуска тестов. Для скилла, состоящего только из инструкций Markdown, отметь покрытие кода как неприменимое. Применимые информационные замечания тоже разбери и при необходимости исправь.
4. На окончательной версии повтори обязательные проверки проекта. Если менялось описание, проверь, что скилл загружается в целевых сценариях и пропускается в несвязанных.
5. В отчёте укажи, какие замечания устранены, какие остались и почему, а также результаты проверок окончательной версии. Публикацию согласуй по действующей процедуре проекта.

## Критерии приёмки

- При оценке A с применимым предупреждением агент пробует минимальную правку, повторяет статический анализ и сравнивает результаты. Неудачная правка оставляет рабочую версию и объяснение.
- Для исполняемого кода проверяется возможность получить артефакт покрытия из реального запуска тестов. Для скилла из инструкций Markdown фиксируется неприменимость покрытия кода. Иные информационные замечания получают объяснение применимости и решение.
- Проверки относятся к окончательной версии. При изменении описания подтверждены загрузка в целевых сценариях и пропуск в несвязанных. Отчёт фиксирует устранённые и оставшиеся замечания, причины и результаты обязательных проверок. Публикация проходит по действующей процедуре.
