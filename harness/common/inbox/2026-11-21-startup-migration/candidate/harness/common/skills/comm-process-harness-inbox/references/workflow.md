# Route, stages and state

Classify purpose/operation before routing:
- All common changes, including reports/memory, use common/inbox.
- Project mechanism changes (structure, agent rules/procedures, executable
  mechanism checks, governing configuration) use project/inbox.
- Authorized creation/update of application ideas, research, decisions, specs,
  plans, handoffs and check results goes directly to permanent project categories,
  without another request; an authorized save is this ordinary route.
  preserve candidate/accepted, planned/implemented and failed/unrun/passed status.
  It does not authorize migration or cleanup of existing materials.
  Before any evidence operation use comm-protect-harness-evidence: new work evidence
  and additions to a current unfinished report are direct; completed corrections
  are new dated linked addenda, raw logs/snapshots immutable. Report state, not age
  or work/ placement, determines whether a report is still current.
Purpose governs, not folder/name/"test": app API contracts are work records;
agent procedures remain mechanism even in docs.
Inspect contents/descendants before parent operations. Mixed mechanism stays
protected; clarify unknown purpose before mutation. Explicit skills retain this boundary.
Approved request creation and permanent results of its authorized execution
are the inbox route. Bypass conditions below govern protected changes,
not ordinary app saves.

Direct bypass requires named material, paths and operation, a separate agent question about bypass, and an unequivocal positive reply after it. Check the conversation. Ask if the question is missing; wait for a clear answer, respect refusal. Initial confirmation, skill invocation, deadlines and operation permission cannot supply that reply. Reuse the pair within unchanged scope. Expansion requires another pair. Only explicit user revocation changes the ordering. Checks, publication approval, protected inputs and template decisions still apply.

Only startup may create an absent neutral project from the agreed skeleton without INBOX. Preserve an existing project and shared template.

Prepare and test the Канидат INBOX in this request. Keep the last publication canonical. Report each client/mode and gaps. Obtain explicit approval for the exact versions, including any gaps, in this request. Publish to canonical first, synchronize working copies only from canonical, verify bytes, then update status. Direct INBOX-to-working copying is forbidden even on request.

Creation, execution (including tests), publication and bypass have separate permissions. One message can grant several; reuse granted stages. Paths, deadlines, an option number or an error grant no missing stage. When separate agreement is required, ask and wait before creation or testing.

When authorized, run targeted checks for changed behavior and full project checks
when compatibility needs them. Creation grants no candidate execution or all
historical editions. Перед запуском тестов прочитай файл `harness/common/skills/comm-install-harness/references/testing.md`.
Report scope/exit/limits: target success is not full, collection not execution.

Create harness/<package>/inbox/YYYY-MM-DD-meaning/ using actual creation date;
disambiguate collisions by meaning. Record need time, circumstances, cause,
problem and result; never invent dates. Instruction requests without confirmed
direct route include full skill folders/resources or complete rule files.

Each request (legacy single-file in its file) has Execution: Status, Result,
Reason, update date. Status new/in progress/completed/blocked/rejected; before
work “not executed”, at start “in progress”. After work/stop record artifacts,
remaining scope/reason; preserve prior results/links. Group accounting is insufficient.
Completed → skip unless repeat requested; in progress → reconcile/resume;
blocked → audit obstacle and continue only if removed; rejected → explicit resume;
missing status → inspect actual evidence, do not infer completed/new, record uncertainty.

Sequential earliest→latest; unclear chronology requires decision, not invented
dates. Do not start next until result and required publication complete or user
explicitly decides closure. Blocked/in progress/prepared candidate is not closure.
Missing authorization/branch/conflict → precise question and wait, no dependent
work. При блокировке разрешениями или автоматической проверкой прочитай файл `harness/common/skills/comm-resolve-permission-blockers/SKILL.md`; known technical
errors within granted scope can be fixed without choosing for the user.
Permanent result stands without inbox; its link is provenance. Accounting or
unverified publication never upgrades agent statuses.
