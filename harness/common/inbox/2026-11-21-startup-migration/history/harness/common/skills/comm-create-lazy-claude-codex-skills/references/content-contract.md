# Content and form

Each new/substantial edit: name behavior, trigger and observable result;
inspect existing skills/rules/resources/tests. Covered → reuse without a new
record; a narrow gap → amend its owner. Own request/result/independent check
→ consider a separate owner; one result's detail → conditional resource.
Theme/old name is not ownership; no skill-count quota.

## Select before authoring

Compare all three forms against the actual need:

| Form | Sufficient when |
| --- | --- |
| Rule only | A short boundary must apply before procedure selection; no separate algorithm is needed. |
| Context-dependent lazy skill only | A recognizable task needs a procedure; name/description can trigger its loading. Default for contextual procedures. |
| Rule + lazy skill | A concrete failure must be prevented before skill selection, lazy metadata is insufficient, and the detailed procedure belongs only in matching tasks. |

For a rule, name the pre-selection failure and explain why lazy discovery cannot
prevent it. Brevity, habit and "more reliable" alone are not evidence. A discovery
miss first calls for improving name/description and checking loading; it does
not automatically justify a rule. Preserve existing mandatory boundaries.

Weigh persistent context cost, discovery, procedural cohesion and drift. Choose
the minimum sufficient form, including reuse/no change. Briefly record why each
of the three forms fits or fails, including rejected alternatives, and the choice
in the authorized request or permanent rationale,
outside working instructions. Make technical choices within existing authority;
this adds no universal user approval gate.

In a pair, the rule owns the necessary early boundary and the skill owns the
algorithm. Duplicating a critical boundary needs specific justification; a
mandatory algorithm alone does not justify an always-loaded rule.

When validation is authorized, test form choice and discovery behavior:
lazy-only, rule-only, justified pair, reuse/amendment, metadata repair and
unrelated non-loading. Use real behavior, explicit/implicit discovery and
both-mode checks under the existing validation owner. Missing checks remain
unverified; drafting the rationale is not proof of discovery.

## Preserve the content contract

Write inputs → actions → result → observable completion, when-read pointers,
missing data/approvals/stops/limits. Headings optional; metadata selects.
Remove repeats/advice/history; examples prevent mistakes.
Rationale/evidence permanent outside instructions/inbox. Preserve obligations/
both-mode dependencies with tested pointers, no mandatory chain of all skills.

When creating or editing a rule or skill, check every by-name dependency,
including existing references in the instruction and its working resources.
Use the exact enabled catalogue name: `plugin:skill` for plugins, the
registered name for local and system skills. Verify one intended owner per
supported host. Preserve when to look up, read and apply it, and its inputs.
If a required name is absent or ambiguous, explain and stop that action.
Keep direct resource links.

Goals: SKILL usually ≤200 words; resource sum ≤1000 static tokens,
resolve >1200 deferred; plugin-eval:evaluate-skill A/no errors. No raised thresholds,
hidden resources or fake manifests/coverage.

Profile: nonempty YAML name/description; name 1–64 [a-z0-9-], no edge hyphen/--,
folder match, shared comm-/proj-; description 1–1024 chars, trigger/capability.
SKILL alone suffices; references/scripts/assets optional guidance/actions/outputs;
agents/openai.yaml UI/policy/deps. Exclude human bodies.
Rules scope/behavior in body, no paths metadata; Claude ignores metadata
except paths. Verify Codex loading separately.
For new/edited always-loaded rules, before drafting/reporting read from root
`harness/common/skills/comm-validate-harness-instructions/references/rule-budgets.md`.
