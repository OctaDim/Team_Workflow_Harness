# Author one instruction

Use superpowers:using-superpowers before authoring. Establish task, useful result, intended
harness and destination; cwd is not proof. Before design/substantial edits read
[content and form selection](references/content-contract.md).

1. Inspect existing owners/rules/resources/checks. Covered → reuse; a small gap
   → amend its owner. Select by independent result, not theme or old name.
2. Compare rule-only, lazy-skill-only and rule+skill before choosing. Record why
   each form fits or fails, then select the minimum sufficient form; default
   contextual procedures to lazy skills. A rule needs a concrete pre-selection
   failure that lazy metadata cannot prevent.
3. Produce inputs → actions → result → observable completion, with limits,
   approvals/stops/missing data and exact tested conditions for resource reading.
4. Before writing follow the authorized inbox route from root
   `harness/common/skills/comm-process-harness-inbox/SKILL.md`; keep a full dated
   candidate and permanent rationale/evidence outside working instructions.

Done: justified form and compact complete candidate preserving every contract
and both-mode dependencies. Design alone is not validation or publication.
When checking is requested use
`harness/common/skills/comm-validate-harness-instructions/SKILL.md`;
when publishing use
`harness/common/skills/comm-publish-harness-instructions/SKILL.md`.
Do not load these stages for an unrelated request. Protected entrypoints and
canonical priority remain mandatory.
