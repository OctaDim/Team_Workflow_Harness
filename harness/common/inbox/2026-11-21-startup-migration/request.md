# Миграция старта harness для Codex и Claude Code

Дата обращения и создания заявки — 2026-11-21 (Europe/Minsk). Пользователь согласовал одну основную INBOX-заявку и разрешил записать решения и критерии приёмки. Выбран маршрут Superpowers + Compound Engineering: согласование требований, затем план, выполнение и проверка. Вопросы согласуются по одному.

Сегодня Claude Code получает импорт `@AGENTS.md` и нативно загружает файлы из `.claude/rules/`. Codex следует маршруту через два `START.md`, файлы из того же каталога и два `INDEX.md`. Этот порядок требует повторных сверок и предполагает возможность управлять очередностью нативной загрузки. Цель миграции — единое поведение клиентов до начала задачи, с проверяемой загрузкой нужных материалов и измеримой стоимостью навигации.

## Словарь для диалогов и материалов harness

При публикации закрепить в канонической части common следующие термины. В диалоге называть конкретный тип.

| Термин | Смысл |
|---|---|
| always loaded правило | Полный актуальный текст требуется при старте до любой задачи. Возможны условные и безусловные ссылки на скиллы. |
| короткое always правило с условным скиллом | Одна или несколько ссылок на скиллы, все условные. |
| короткое always правило с безусловным скиллом | Одна или несколько ссылок на скиллы, все безусловные. |
| короткое always правило с условным\безусловным скиллом | Есть ссылки обоих типов. У каждой свой момент чтения. |
| контекстный lazy скилл | До выбора доступны `name` и `description`. При выборе клиентом или наступлении условия ссылки агент получает полный актуальный `SKILL.md` до зависимого действия. |
| Защищённые `AGENTS.md` и `CLAUDE.md` | Два корневых входа Codex и Claude Code соответственно. |
| Канидат INBOX | Версия материала в текущей INBOX-заявке, подготовленная к проверке и решению о публикации. Написание термина задано пользователем. |

## Старт и защита входов

- Для Claude Code корневой `CLAUDE.md` пуст. Codex получает из корневого `AGENTS.md` единственное указание прочитать до задачи все always loaded правила в `.claude/rules/` и его подпапках, исключая `README.human.md` на любой глубине. Удалить зависимость старта от обоих `START.md`. Обязательность карт `INDEX.md` определить по отдельному сравнению ниже.
- Стартовую проверку перед задачей запускает общее always loaded правило. Если утрачен вход Codex или само это always loaded правило, для восстановления предусмотрен отдельный запуск существующего скрипта. Сохранить автоматическое создание только отсутствующего нейтрального `harness/project` в режиме переноса common. Обычный старт сохраняет существующий project. Проверить оба режима установки и повторный старт.
- Защищённые `AGENTS.md` и `CLAUDE.md` доступны агентам и пользователям только для чтения по договорённости harness. Отсутствующий файл создавать из согласованного канонического образца. При отличии существующего файла показать различие, остановиться до задачи и вынести исправление на явное решение пользователя через INBOX. Согласованная миграция существующего `@AGENTS.md` проходит через публикацию.
- При изменении любого входа сверить оба с их собственными образцами и отдельно проверить равнозначность поведения Codex и Claude Code. Обнаруженный конфликт согласовать с пользователем. Неполная проверка возможна только по описанному ниже порядку публикации.
- Если в `.claude/rules/` обнаружено дополнительное always loaded правило без канонического источника, остановиться до задачи, показать путь, сохранить файл для решения пользователя. Для принятия в проект использовать project INBOX. Удаление требует явного решения.

## Загрузка и применение

Любая ссылка на скилл сама по себе не загружает его текст. Безусловная ссылка требует получить полный `SKILL.md` сразу после получения always loaded правила и до начала задачи. По условной ссылке агент сам распознаёт момент наступления условия, включая его наступление в середине задачи. Краткость always loaded правила и количество ссылок этого не меняют.

Перед задачей сверить ожидаемый набор always loaded правил с полными актуальными текстами в контексте. Если получение файла уже подтверждено в этой сессии, использовать полученный текст. Недостающий открыть, обрезанный дочитать до конца в той же версии. При невозможности получить полный требуемый текст остановиться, указать путь и причину и дождаться решения пользователя. Для контекстного lazy скилла выполнить ту же проверку при выборе или наступлении условия до зависимого действия. Само чтение не даёт разрешения на операцию.

Проверять каждого нового или изменённого контекстного lazy скилла по нативному выбору через `name` и `description`, включая скиллы, связанные с коротким always правилом. Для связанных скиллов проверить также каждый тип ссылки, положительный и отрицательный контекст. Пример: объяснение конфигурации не активирует условие «перед изменением конфигурации». При запросе на правку или выявленной необходимости правки полный текст должен быть получен до её начала. Отдельно проверить полную выдачу, обрезанный вывод и ошибку чтения. Фиксировать способ получения текста (при старте, при нативном выборе или явным чтением), отсутствие лишних полных чтений и наблюдаемое применение в нужный момент.

## INDEX и область поиска

Оставить оба INDEX картами каталогов. По каждому требованию к поведению установить действующего владельца, сохранить условия и исключения до удаления повтора. Границы поиска перенести в существующее always loaded правило [comm-human-folder-guides.md](/harness/common/rules/comm-human-folder-guides.md). До первого поиска агент знает, где искать актуальные материалы, когда допустимо открыть inbox или evidence и почему при выборе заявки сначала читают статусы. Процедуры обработки заявки, защиты входов, исключения человеческих пояснений и записи evidence сохранить у соответствующих владельцев. Не добавлять второй каталог нативных описаний или отдельный скилл для чтения карты.

В двух изолированных вариантах обеспечить одинаковые требования к поведению, карты и нативные описания. В одном обе карты обязательны при старте, в другом доступны по необходимости. Для каждого клиента и режима установки сравнить правильность выбора, открытые файлы, лишние и пропущенные чтения и входные токены до содержательной работы. Отмечать фактические измерения и пробелы. Проверить задачу без контекстного lazy скилла и поиск актуального материала при похожем историческом снимке в evidence. Проверить и ответ, и область фактического поиска. Показать результаты пользователю. Если выбор одинаково корректен, а обязательное чтение дороже, предложить карты по необходимости. Решение, включая расхождение между клиентами, согласовать после отчёта.

## Источник, публикация и восстановление

Единственный источник для проверки, синхронизации и восстановления рабочих копий — соответствующие канонические файлы в `harness/common` или `harness/project`. Исключить поддеревья inbox из поиска этих источников. Пока Канидат INBOX проверяется в текущей заявке, в канонической папке остаётся последняя опубликованная версия.

1. Подготовить отчёт по точной версии каждого файла с результатами по Codex и Claude Code отдельно для `common-only` и `common+project`. Для каждого обязательного сценария указать ожидаемый результат, фактический результат или причину пропуска. Различать «пройден», «не проверен» и «не пройден». Описать ошибки и известные причины. После изменения содержимого заново проверить и одобрить версию.
2. Получить явное разрешение на публикацию перечисленных точных версий. При неполной проверке, в том числе для защищённых входов, пользователь может разрешить публикацию в той же INBOX-заявке после отчёта с перечисленными пропусками. При неоднозначности уточнить и ждать. Выявленное расхождение требует исправления, конфликт поведения защищённых входов — отдельного решения. Статус публикации сохраняет фактическую сводку проверок, например `Codex — проверено / Claude Code — не проверено`.
3. Перенести одобренное содержимое в каноническую папку. Синхронизировать рабочие копии только из неё, проверить побайтное совпадение, затем обновить статус текущей заявки. Прямое копирование из INBOX в рабочие папки запрещено, в том числе по просьбе скопировать ещё неопубликованную версию.
4. Взаимозависимые файлы публиковать одним согласованным набором с точными версиями всех участников. Изменившаяся версия требует нового одобрения до публикации набора. Если переход прервался, старт останавливается до задачи; продолжение — в той же заявке. Закрытие — после сверки всего набора.
5. При потере или повреждении управляемой рабочей копии восстанавливать её из опубликованного канонического файла. Если в контекст клиента уже попал старый текст, проверить исправленный старт в новой сессии. Для защищённых входов действует описанное выше различие между отсутствием и расхождением.

Критерий приёмки: в канонической папке версия 1, в INBOX версия 2. Удалить рабочую копию в изолированной установке и проверить восстановление версии 1. После одобрения и публикации версии 2 повторить проверку до и после удаления закрытой заявки в тестовой копии. Проверить также повреждённую копию, попытку прямого копирования и прерывание публикации связанного набора.

## Миграция ссылок и сроки хранения

- Проверять нерабочие внутренние ссылки только в рабочем harness, включая установленные копии. Для новой или исправленной рабочей ссылки использовать точное имя цели с сохранением регистра, один `/` от корня репозитория и фактический идентификатор раздела, если он указан. Для рабочих файлов `README.human.md` проверка программная.
- Исторические артефакты исключены из проверки и исправления ссылок. Это относится к исходникам ссылок в завершённых заявках, прежних Канидатах INBOX, свидетельствах и снимках. Рабочую ссылку на артефакт проверять со стороны рабочего файла, без обхода внутренних ссылок артефакта.
- В `history/harness/` сохранить с прежними путями текущее состояние каталога `harness/` до переключения. Отдельные исторические редакции файлов из Git для ремонта переходов в артефактах не добавлять. Пользователь выбрал действующую часть обоих пакетов и текущую INBOX-заявку вместе с её Канидатом INBOX. У категорий INBOX, evidence, handoffs и планов сохраняется каркас с человеческими пояснениями. Другие заявки, исторические отчёты, передачи задач, старые планы и кэши исключены. Каталог назначения и временный архив U1 исключены из содержимого снимка. Ведомость проверки составляется после копирования и хранится рядом с каталогом снимка. Исходную сохранность проверять по составу и байтам.
- В рабочем harness также учесть ссылки, цель которых исчезает при переключении. Для перенесённого требования выбрать действующего владельца, для снятого этапа старта зафиксировать причину удаления. Для каждого изменения рабочего перехода записать исходную ссылку, действие и результат проверки. Публикация подготовленных файлов проводится через текущую INBOX-заявку.
- Сохранить архив до полной проверки и приёмки пользователем. Затем закоммитить архив, отправить коммит и подтвердить его доступность в удалённой ветке. Только после подтверждения удалить из рабочего дерева временный архив и ссылки на него, зафиксировать удаление следующим коммитом. Итоговый отчёт охватывает ссылки рабочего harness. Снимок каталога сохраняется по пути `history/harness/` этой заявки.

## Дальнейшие стадии и границы

После разрешения на выполнение: провести инвентаризацию, сопоставить действующие требования с владельцами и проверками, согласовать спецификацию и план до зависимых изменений. Учитывать отдельные действующие согласования для изменений механизма project или общего шаблона каркаса, если такая правка действительно нужна. В изолированных установках проверить оба клиента, режимы и повторный старт, нейтральное создание отсутствующего project, сохранение имеющегося project, чтение и применение, режимы восстановления, точные ссылки и затраты на INDEX. Согласовать оставшиеся развилки по одной. Публикация требует отдельного разрешения по отчёту на точные версии.
