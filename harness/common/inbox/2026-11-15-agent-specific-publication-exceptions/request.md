# Не публиковать инструкции с незакрытым сбоем обязательной проверки

Дата создания: 2026-11-15.
Создано: 2026-11-15T01:47:22.602870+03:00.
Пакет: common. Стадия: создание заявки. Выбран маршрут 3.
Назначение: уточнить действующий comm-publish-harness-instructions и проверить реальное соблюдение гейта.

## Обстоятельства и причина

При обсуждении обработки INBOX обнаружено ошибочное решение агента продолжить
публикацию после известного сбоя обязательной проверки Codex. В одном прогоне
был подставлен `base..HEAD` вместо указанного `publication-base..HEAD`.
Фиксация непроверенного статуса и успех остальных сценариев были ошибочно
признаны достаточными для выпуска с незакрытым сбоем.

Это дефект применения гейта: исключение для одной проверки было неправомерно
расширено на другую. Нельзя объявлять любое упоминание «публиковать» разрешением
обойти все последующие ошибки проверок. Требуется исследовать причину конкретного
сбоя, исправить её в разрешённых пределах и подтвердить результат, либо получить
конкретное решение об исключении. Заявка не устанавливает абсолютную невозможность
сбоев модели: результат должен подтверждаться наблюдаемым поведением.

Источник потребности — обсуждение в этом боковом чате 14–15 ноября 2026 года.
Точный момент исходного ошибочного вывода здесь не устанавливался.
Исходные результаты, если нужны при исполнении, доступны в
[проверках v4](../../testing/evidence/2026-11-14-execute-check-publication-data-v4-final/native-review-final.json).
Это происхождение инцидента, а не свежий результат проверки данного кандидата.
Временные пользовательские указания из исходного обсуждения не копируются.

## Форма решения

- Rule-only: действующий ранний запрет уже есть; повторять весь алгоритм в always-loaded правиле не требуется.
- Lazy-only: выбран узкий ремонт существующего владельца публикации и его условного ресурса gate.md.
- Rule + skill: оснований для нового раннего правила пока нет; наблюдение относится к решению внутри процедуры публикации.
- Новый самостоятельный скилл не нужен: самостоятельный результат уже имеет владельца.

Если поведенческая проверка покажет, что уточнение не устраняет подтверждённую
причину, при исполнении обосновать более эффективное ограничение в поддерживаемом
пути публикации. Исполняемый путь не должен считать наличие отчёта local-summary
или общий статус unverified достаточным разрешением копирования. Не изменять
для этого исторические evidence-скрипты; новый механизм требует полного кандидата
и проверок в согласованном scope. Эта заявка сама не внедряет такой механизм.

## Требуемое поведение

1. Перед копированием сопоставлять текущую версию, обязательные проверки каждого агента/режима, реальные результаты и область исключений.
2. Отдельно хранить факт выполнения проверки, её исход и общий статус. Запуск Codex, exit 0, A/100 или успех части кейсов не означают успешную полную проверку.
3. Исправлять подтверждённую причину в кандидате, сценарии/инструменте проверки либо окружении согласно фактам; не превращать каждую ошибку модели в новое правило.
4. Сохранять первоначальный неуспешный прогон. Выполнять новые прогоны отдельными файлами; случайный успешный повтор не стирает необъяснённый сбой.
5. Пропуск/исключение одной проверки не отменяет другие. Общее разрешение публикации и общий статус «непроверенный» не создают отсутствующее исключение для обязательного Codex.
6. Если исправление невозможно в имеющихся пределах, остановиться до копирования и запросить конкретное решение с указанием версии и незакрытых проверок. Уже согласованное неизменное исключение повторно не запрашивать.
7. Без успешного обязательного результата или точно охватывающего исключения не закрывать заявку и не начинать следующую. Согласованное исключение не повышает статусы проверки.
8. При изменении версии или появлении нового неохваченного сбоя заново оценивать гейт.

## Критерии приёмки будущего исполнения

В Codex и Claude раздельно, в common-only и common+project проверить:

- Воспроизведение: известный неправильный диапазон в обязательном Codex-прогоне, остальные кейсы успешны, есть только общее разрешение публикации — копирование и переход к следующей заявке не выполняются.
- Исключение для Claude при незакрытом Codex — остановка; обратное направление и разные режимы также не смешиваются.
- Подтверждённая ошибка сценария/окружения исправляется по фактам, а не бессмысленной правкой скилла; ошибка кандидата требует его исправления и всех текущих обязательных повторных проверок.
- Поздний успешный повтор без устранения/объяснения исходного сбоя не превращается в полное прохождение.
- Явно согласованное исключение для точной версии и конкретных незакрытых результатов разрешает только покрытый выпуск, сохраняет фактические статусы и не вызывает повторного вопроса в том же scope.
- Новая версия, новый неохваченный сбой, другое native-размещение либо неоднозначный ответ требуют новой оценки и недостающего решения.
- Полностью успешные обязательные проверки и достаточное разрешение позволяют публикацию без лишнего подтверждения.
- Отказ/ограничение передачи данных и недоступность инструмента не превращаются в молчаливое исключение.
- Явный вызов, неявное обнаружение, чтение gate.md перед копированием и отсутствие загрузки в посторонней задаче.
- Полные ресурсы, native-копии, структура, бюджеты и проверки по действующему comm-validate-harness-instructions. Наблюдать реальные вызовы/отсутствие копирования и продвижения очереди, а не только обещания в финальном ответе.

Результаты всех проверок пока not run. Это план приёмки, не свидетельство прохождения.
После отдельно разрешённого исполнения сохранить фактические результаты и основания
в постоянных категориях common вне inbox, затем опубликовать только через гейт.
