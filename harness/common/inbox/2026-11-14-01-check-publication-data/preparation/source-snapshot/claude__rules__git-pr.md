# PR и коммиты — инварианты (всегда загружено)

## 🛑 Squash ветки, не содержащей ВЕРШИНУ `main`, ОТКАТЫВАЕТ чужой мерж — целиком и молча

Наш squash-мерж ставит один коммит с ОДНИМ родителем, а дерево берёт из ветки. Значит всё,
что приехало в `main` после того, как ветка от него отошла, в этом дереве отсутствует — и
squash сносит это как удаление файлов. Пострадавший PR при этом остаётся `MERGED`, его коммит
виден в истории, `git log` выглядит нормально: пропажу показывает только `git show --stat`
твоего коммита, где стоят чужие минусы.

**Fails-when:** между заведением ветки и мержем прошли минуты, и в них кто-то смержил своё —
самый обычный день, когда команда мержит каждые 20-30 минут. Своя правка при этом крошечная,
конфликтов нет, гейт зелёный, поэтому «догнать `main`» кажется формальностью. `mergeable`/
`mergeStateStatus` не спасает: у виновного PR он стоял `UNKNOWN` (замер ниже).

**Порядок — арбитр ПЕРЕД мержем, одна команда после свежего `fetch`:**

```bash
git fetch origin && git merge-base --is-ancestor origin/main <ветка>   # rc=0 обязателен
```

`rc≠0` значит «ветка не содержит вершину `main`» ⇒ сперва `git merge origin/main` (ветка
опубликована — только мержем, не ребейзом), прогнать гейт заново и лишь потом мержить. То же
показывает `gh pr view N --json baseRefOid` в сверке с `git rev-parse origin/main`.

**«Прогнать гейт заново» решает выборка по ДЕЛЬТЕ, а не заголовок чужого PR:**
`uv run python -m scripts.pytest_diff --dry-run --base <SHA, на котором гейт был зелёным>`.
Выборка пуста — перегон холостой, push с `--no-verify` законен (случай «гейт не про твою
правку» из раздела ниже; сказать вслух). Есть тесты или код 2 — гейт заново. С 11.09 хук
делает это сам (`--since-green`): база — последний зелёный прогон этого воркти. Замер
10.09.2026: PR #1473 «закрытие воркти, план разложен» выглядел одними доками, а нёс +8 строк
в `src/` и правку `HANDOFF.md` — выборка дала 5 тест-файлов.

**После мержа СВОЕГО PR — обязательный контроль:** `git show --stat <мой squash-коммит>`, и в
нём не должно быть ни одного файла, которого ты не трогал. Минусы в чужих путях = ты откатил
чужую работу, чинить немедленно (вернуть их содержимое из последнего доброго коммита отдельным
PR, а не revert'ом своего — иначе уедет и своя работа).

**Замер 10.09.2026 (цена — 2390 строк чужой работы):** PR #1464 (сид площадок погрузки) был
заведён от `27bbfdd5`; за шесть минут до его мержа в `main` уехал PR #1450 (`ab1aa057` — гейт
`pre-push`, таймаут тестов, число воркеров). Squash дал коммит `bb3663d9` с родителем
`ab1aa057` и деревом ветки, то есть **удалил `.githooks/pre-push`, его тесты и мутанты, урезал
`pytest_diff.py`, `conftest.py`, `pyproject.toml` и план соседнего воркти** — ровно зеркально,
`+2390/−2390`. Ни один гейт этого не заметил; нашлось вопросом владельца «ты удалил коммиты
про тесты?» и починено отдельным PR #1465. 🛑 Родственное правило про стек веток
(`~/.claude/rules/git-flow.md`) описывает случай «предок ⊂ потомок»; здесь стека нет вовсе —
достаточно ОДНОГО чужого мержа, приехавшего после ответвления.

## 🛑 Текст PR и коммита — ТОЛЬКО файлом, никогда инлайном

Описание PR и сообщение коммита — через файл: `gh pr create/edit --body-file`, `git commit -F`.
Инлайн в двойных кавычках запрещён: шелл исполняет `` `бэктики` ``, а их в наших описаниях полно
(имена функций, полей API), и делает это МОЛЧА — PR создаётся, дыра видна только при перечитывании.
`--title` инлайном можно (короткий, без бэктиков; появился бэктик → переписать прозой). Уже уехало
с дырой — чинить прямым PATCH (см. «`gh pr edit` МОЛЧА не применяет body» ниже), не комментом.

## 🛑 `--no-verify` — не способ обойти красный гейт

С 10.09.2026 в репозитории лежит `.githooks/pre-push`: у того, кто включил его командой
`git config core.hooksPath .githooks`, каждый `git push` сперва гоняет выборку по диффу
(секунды на узкой, минуты — если дифф задел общий модуль) и не отправляет ветку, если она
красная или изменённый модуль не покрыт ни одним тестом (код 2). Хук сам печатает `--no-verify` как
аварийный выход — и именно поэтому флаг под запретом там, где он выглядит удобнее всего.

**Fails-when:** push отбился, разбирать красное долго, а работа «уже готова». Отказ тихий:
ветка уезжает, PR выглядит нормальным, красное всплывает у человека при мерже.
**Порядок:** `--no-verify` законен ровно в двух случаях — гейт не про твою правку (чужой
незакоммиченный мусор в том же воркти) или отправляешь заведомо промежуточное состояние и
сказал об этом вслух. Красный гейт по своей правке чинится, а не обходится.

🛑 **Claude Code сам переписывает `core.hooksPath` при создании воркти:** относительный
`.githooks` становится абсолютным путём основного чекаута (замер 10.09.2026, 2.1.267, дважды
за день). Хук тогда исполняется из основного чекаута; отстал тот от `main` — файла нет, и push
уходит без гейта МОЛЧА. Арбитр — последняя строка `pytest_diff` («гейт … не сработает — git
ищет хук в …») или `git config --show-origin --get core.hooksPath`, а не память «хук включали».

## 🛑 Force-push НЕ стирает коммит с GitHub — секрет читаем по старому SHA

Переписал историю убрать секрет — локально `git log` чист, но объект на GitHub отдаётся по прямому
старому SHA (`gh api …/contents/FILE?ref=<old-sha>`). Перед словами «секрет вычищен» — проверь, что
старый SHA даёт 404; не 404 → формулировка «переписал историю», а не «удалил». Настоящее удаление —
только GitHub Support. Секрет всё равно РОТИРОВАТЬ (часть значений, напр. id Google-дока по ссылке,
отозвать нельзя в принципе).

## 🛑 Ненулевой код `gh` — про ПОСЛЕДНЮЮ команду цепочки, не про операцию

`gh pr merge N && gh pr view N` даёт `exit 1` от упавшего `view` (таймаут к api.github.com частый),
хотя merge прошёл. Перед повтором необратимой gh-операции — отдельный read-only запрос состояния
(`gh pr view N --json state,mergedAt`), решение по нему. Необратимую команду не склеивать с
проверочной через `&&`.

🛑 **Тот же класс НАОБОРОТ и опаснее: `git push … | tail` даёт код НУЛЕВОЙ на упавшем push.**
Код пайплайна — от последней команды, а `tail` успешен всегда. **Fails-when:** гонишь push
фоном и красиво режешь вывод; задача рапортует «exit code 0», в выводе при этом
`fatal: unable to access … Failed to connect`, а ветки на удалёнке нет. Замер 31.08.2026 —
поймано только сверкой состояния. **Порядок:** сетевую команду не пайпить вовсе (нужен
короткий вывод — читай файл задачи потом), а «уехало ли» решать `git ls-remote origin
refs/heads/<ветка>` со сверкой SHA против `git rev-parse HEAD`, не кодом возврата.

## 🛑 `gh pr edit` МОЛЧА не применяет body — падает на Projects-classic

`gh pr edit --body-file` возвращает `rc=1` на deprecated Projects-classic GraphQL
(`repository.pullRequest.projectCards`), а описание НЕ обновляется. Симптом маскируется под
`i/o timeout` или строку deprecation-warning — оба читаются как «прошло с оговоркой».
**Fails-when:** обновляешь body через `gh pr edit`, видишь warning/таймаут, считаешь применённым —
`gh pr view --json body` показывает СТАРЫЙ текст. **Обход:** прямой REST
`gh api -X PATCH repos/OWNER/REPO/pulls/N -F body=@<файл>` (текст ФАЙЛОМ через `-F …=@`, не argv;
вернул номер PR = успех), применение проверять отдельным read, не по `rc` от `gh pr edit`.

Разбор: `/git-pr-history` — zsh-раскрытие, замеры PR #415/#423/#646/#696, TE-66.

## 🛑 «Ahead N» и `git cherry` НЕ доказывают, что работа не выпущена

Мы мержим **squash'ем**: коммит остаётся в ветке со своим SHA и своим patch-id, а в `main`
лежит его склейка. Поэтому `git rev-list --count origin/main..<ветка>` и `git cherry`
помечают уже выпущенную работу как уникальную — оба считают коммиты, а выпущено содержимое.

**Fails-when:** видишь «ahead 13», объявляешь работу потерянной и начинаешь пересаживать
коммиты — половина уже в проде, пересадка даёт конфликты на пустом месте. Замер 31.08.2026:
из 13 «неопубликованных» коммитов реальными были **4**; из 23 веток, помеченных `git cherry`
как уникальные, невыпущенной была **одна**.

🛑 **Диффом сверять тоже нельзя.** `git diff origin/main..<ветка>` на отставшей ветке
показывает уход `main` ВПЕРЁД, а не отсутствие работы: «+» строки — это старый код, который
`main` с тех пор выбросил. Читается как «в ветке есть уникальное» и врёт в ту же сторону.

🛑 **И зеркально — самый тревожный вид того же вранья: дифф отставшей ветки печатает УДАЛЕНИЯ
чужих файлов, и это читается как «мы откатили чужую работу».** Отличие от абзаца выше — в
цене вывода: там теряют своё, здесь начинают искать несуществующую порчу, а при спешке могут
«вернуть» чужое руками поверх мержа. **Fails-when:** проверяешь ветку на регресс, а между
твоим последним `fetch` и этой проверкой в `main` влились чужие PR — и окно для этого шире,
чем кажется: собственный pre-push гейт идёт МИНУТЫ, а команда мержит каждые 20-30 минут
(замер 14.09.2026: за один шестиминутный push влились три PR, в следующий раз ещё три).
**Порядок:** прежде чем толковать минусы в диффе — свежий `fetch` и
`merge-base --is-ancestor origin/main HEAD`; rc≠0 значит «ветка отстала», и дифф
описывает отставание, а не порчу. Вердикт о порче выносить только после догонки,
повторив ту же команду.

🛑 **Отставание бьёт не только по чтению — оно делает ветку КРАСНОЙ по чужой причине.**
Чужой PR чинит `main`, у тебя его нет, и твой прогон падает на тесте, который ты не трогал:
свой дефект и отставание в выводе pytest неразличимы. **Fails-when:** сторож синхронизации
двух списков (зеркальный enum, набор ролей, таблица прав) — у нас это
`tests/fixtures/test_fixtures.py::test_factory_enums_align_with_db_models`. **Порядок:**
красный тест в файле, которого нет в твоём диффе, — сперва догнать `main` и перепрогнать,
и лишь потом расследовать. (Замер 14.09.2026: `Extra items in the right set: 'GNB'` — фикс
приехал чужим PR #1595, после догонки тест зелёный без единой нашей правки.)

**Порядок.** Арбитр — СОДЕРЖИМОЕ, а не счёт:
1. `gh pr list --state all --limit 200 --json number,state,headRefName` и матч по имени
   ветки. Есть `MERGED` — работа выпущена, дальше не смотрим.
2. PR нет или он `OPEN` — берём из его описания то, что он обещал, и проверяем каждый пункт
   в `main` поимённо: `git show origin/main:<файл>`, греп ключевого символа
   (`git grep -c '<символ>' origin/main -- src/`). Пусто по ВСЕМ пунктам — работа реально не
   выпущена.

Разбор: `/git-pr-history` (раздел «Ahead N и git cherry — замер 31.08.2026»).

## 🛑 Мерж поверх пишущего агента — конфликты разрешит агент, не ты

Не мержить, не ребейзить, не пуллить в файлы, в которые ещё пишет агент: его правки и мерж
переплетутся, и конфликты он разрешит по своему суждению, а не по твоему решению. Сначала
останови агентов или дождись их — мерж не операция, терпящая параллельного писателя.

**«Нет маркеров конфликта» ≠ «разрешено как решено».** Это два разных утверждения, и первое
не проверяет второе. После мержа, где ты задал резолюции сам, — грепни файл на решённые
строки (символ, который требовал оставить, атрибут, который требовал убрать), а не по
`git status`, не по отчёту резолвера и не по зелёному прогону тестов: у обеих версий может
быть свой зелёный прогон. Отчёт резолвера — версия, а не факт, тот же принцип, что и везде.

**Fails-when:** раздаёшь резолюции по конфликтам, `git status` возвращается чистым, и
принимаешь это как доказательство, что решения применены. Арбитр — `git grep '<символ>'
<файл>` на разрешённом файле.

## 🛑 Открытый хвост перед выходом ПЕРЕПРОВЕРЯЮТ замером — он протухает за часы

Правило выше про то, что за время сессии уезжает `main`; это про то, что за то же время
успевают **закрыть твои открытые пункты**. Хвост — утверждение об ОТСУТСТВИИ («ещё не
сделано», «не снят»), а такие гниют быстрее всех: отменяет их один чужой PR, и перечитывать
их никто не идёт.

**Fails-when:** закрываешь сессию и переносишь `## Next steps` в план воркти, описание PR или
задачу. Особенно на пунктах «зона другого человека» — их пишут ровно тогда, когда этот
человек в теме прямо сейчас, то есть в момент максимальной вероятности, что он её и закроет.

**Порядок:** по каждому пункту один живой замер, а не перечитывание — `git log --oneline
origin/main -10` на чужие PR по теме, вердикт **содержимым** (`git grep` по имени механизма
в `origin/main`, голова alembic на проде, статус задачи). Переживший проверку помечать датой
замера; закрытый писать как **снятый с указанием, кто и чем**, а не удалять молча.

**Замер 04.09.2026:** из четырёх хвостов сессии два умерли в тот же день — механику заведения
в Медикум сменил PR #1107 (часы), а триггер `trg_shift_waybill_equipment_assignment_update`
сузил PR #1111 (**двадцать минут** после записи, уже выкачено `deploy-20260904-22`). Оба
пункта успели уехать в план, session-заметку и memory, и правились задним числом.

## 🛑 Сначала догнать `main`, потом итоговый гейт и push

**Fails-when:** итоговая выборка уже зелёная, но перед push делается rebase: проверенный
коммит перестаёт быть предком HEAD, зелёная отметка сбрасывается и та же пачка идёт снова.
**Порядок:** во время работы — узкие проверки текущей правки. Когда работа готова,
обновить `origin/main` и догнать его ДО итогового гейта. Для неопубликованной ветки:

```bash
git fetch origin
git rebase origin/main
uv run python -m scripts.pytest_diff
git push origin HEAD
```

Это последовательные шаги: при ошибке остановиться. После rebase разрешить конфликты,
сверить общие номера SW-кэшей с живым продом и закоммитить все итоговые правки ДО тестов.
Для опубликованной ветки вместо rebase — `git merge origin/main`, как указано выше.
Итоговый прогон — без сужающего хвоста и своей `--base`, на чистом дереве; полный сьют
агент не запускает. После зелёного гейта сразу push: включённый pre-push использует отметку.
Открытие PR само по себе нового rebase и прогона не требует. Перед мержем остаётся свежий
`fetch` и проверка предка из первого раздела. Если `main` снова ушёл вперёд — догнать его
и проверить новую дельту; изменения кода после гейта также требуют новой проверки.
Пин порядка: `tests/scripts/test_final_gate_order.py`; переиспользование отметки:
`tests/scripts/test_pytest_diff.py::test_a_push_right_after_a_green_run_runs_nothing`.

## 🛑 После squash-мержа — сверка patch-id: main мог уехать между проверкой и кнопкой

`merge-base --is-ancestor` отвечает про момент проверки, а GitHub кладёт squash на main в
момент мержа: влили за эти секунды чужой PR — коммит ляжет поверх него, и дерево мержа будет
отличаться от твоей ветки на весь чужой PR. **Порядок после мержа:** `git rev-parse <merge>^`;
не база ветки — сравнить `git diff <база> <голова ветки> | git patch-id --stable` с
`git diff <merge>^ <merge> | git patch-id --stable` (совпали — легло ровно твоё) и проверить,
что `git diff --name-only <база> <merge>^` не пересекается с твоими файлами. (Замер
10.09.2026, PR #1478: между проверкой и мержем влился #1477, patch-id совпал.)
🛑 **База — не точка ответвления, если в ветку вливали `origin/main`** (так велит раздел
выше): тогда patch-id расходится на всё влитое, и тревога ложная. База —
`git merge-base <merge>^ <голова ветки>`; при `<merge>^`, равном влитой вершине, достаточно
пустого `git diff <голова ветки> <merge>`. (Замер 27.09.2026, PR #2010.)

## 🛑 Более новый PR не обязан быть НАДМНОЖЕСТВОМ старого — сверять деревьями, а не глазами

Пункт выше про то, выпущена ли работа; этот — про то, что уникального осталось в **другом**
открытом PR того же автора по той же задаче. Отказ необратим: закрыл «перекрытый» PR —
его уникальные файлы исчезли, и ни один сигнал не предупредил.

**Fails-when:** второй PR выглядит новее и содержит все версии артефакта, поэтому первый
закрывают как поглощённый. Автор скопировал в новую ветку папки с работой, но не служебные
файлы соседней — а `mergeable` зелёный у обоих, и Files changed у второго ДЛИННЕЕ.

**Порядок перед закрытием PR как перекрытого** — разность полных деревьев обеих веток:

```bash
git diff --name-status origin/<ветка-A> origin/<ветка-B> | grep -E '^A'
```

И отдельно diff КАЖДОЙ ветки против `origin/main`: расхождение может быть не работой
автора, а **отставанием** — перенос оттуда стал бы откатом чужого.

**Замер 02.09.2026** (TE-56, PR #798 → #799): 128 строк run-book жили только в старой
ветке — их не было ни в `main`, ни в новой. Из 17 остальных «расхождений» все 17 оказались
отставанием старой ветки по чужой папке прототипа.
