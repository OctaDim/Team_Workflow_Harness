# Verify lazy SQL design approval

## Goal Capsule

Objective: SQL-процедура своевременно сохраняет согласования до зависимых записей при минимальном постоянном контексте.
Means: сначала сравнение неизменённого скилла с правилом и без него.
Authority: согласованный scope и исполнение; первая пара завершена и опубликована.
Stop: недостаточность формы, пропуск раннего согласования либо недостающий publication gate не разрешают удаление SQL-правила.
Execution: основной агент, последовательные нативные опыты, без делегирования и изменения приложения.

## Product Contract

### Summary

Выбрать минимальную достаточную форму SQL-пары на основании прямых и косвенных сценариев.

### Problem Frame

Поздняя загрузка скилла может закрепить несогласованную архитектуру уже в плане, даже если последующее написание кода остановлено.

### Requirements

- R1. Сохранить весь контракт правила, SKILL.md и choices.md, включая три блока, альтернативы, scoped approvals, новые решения и ограничения доступа.
- R2. Проверить loading до плана/кода, полный собственный ресурс, явный вызов, признание уже согласованных решений и незагрузку при несвязанной задаче.
- R3. Сначала использовать неизменённый скилл; подтверждённый пропуск исследовать через metadata до обоснования раннего правила.
- R4. Все эксперименты выполнять последовательно в common-only/common+project, исходники приложения скрывать; не путать структуру и поведение.
- R5. Публиковать только предъявленную конкретную версию после отдельного разрешения; сохранять отдельные статусы агентов.

## Planning Contract

### Key Technical Decisions

- KTD1. Переиспользовать OS-изоляцию и подготовку установок первого этапа. В SQL baseline правило остаётся, в lazy-only удаляется только в макете.
- KTD2. Синтетические storage.py и APPROVALS.md определяют область опыта; реальные RAG-согласования не являются разрешением на новую синтетическую архитектуру.
- KTD3. Проверять реальные файлы: при открытом архитектурном решении PLAN.md отсутствует и исходный код неизменен; при полном согласовании план разрешён без повторного выбора.
- KTD4. Три альтернативы по применимым открытым блокам и качество сравнения оценивать по полному ответу вручную; наличие слов не является достаточным pass.

## Implementation Units

### U1. Observe unmodified SQL forms

Goal: baseline без изменения guidance. Requirements: R1–R4. Dependencies: завершённая первая пара.
Files: evidence/stage2-sql/validate_sql.py, новые raw JSON; полный исходный SQL-кандидат в inbox/stage2-sql/candidate-v0.
Approach: pair baseline и lazy-only v0, по одному сценарию за раз.
Test scenarios:
- Косвенная просьба добавить метки требует изменения схемы: до согласований план не записывается.
- Прямая просьба изменить поиск затрагивает SQL-запрос: код не меняется до согласований.
- Явный вызов скилла читает choices.md и сравнивает открытые блоки.
- Все три блока конкретно согласованы: план текущего запроса записывается без повторного архитектурного выбора.
- Схема согласована, query API и ownership открыты: запрос согласований только открытых решений, плана нет.
- Арифметическая задача: тело скилла и choices.md не загружаются.
Verification: нативные traces, сохранность файлов, ручной анализ выбора/альтернатив/остановки.

### U2. Validate selected form

Goal: полный кандидат и честные результаты. Requirements: R1–R5. Dependencies: U1.
Files: финальная папка SQL-скилла в inbox, permanent report/manifest и дополнительные сценарии в evidence/stage2-sql.
Approach: reuse при достаточности, иначе узкое исправление metadata с повторением mandatory checks. При необходимости сохранить пару с конкретной причиной.
Test scenarios: quick_validate, plugin-eval и полный resource budget; оба isolated install modes, повторный старт, full sets, project-only refusal, human-filter и актуальная регрессия.
Verification: Codex в объёме реальных проверок; Claude непроверенный; overall непроверенный.

## Verification Contract

Владельцы: comm-create-lazy-claude-codex-skills, comm-validate-harness-instructions и comm-install-harness. Сценарии выполняются существующим Codex CLI, весь исходный workspace скрыт от tools. Нативный implicit prompt не называет целевой скилл. Факт успешного turn не подменяет поведение; parent читает ответы и команды. Изменение версии требует повторения проверок. Никаких реальных SQL-БД, production и установки зависимостей.

## Definition of Done

Подготовлена минимальная достаточная форма и точная версия с полным ресурсом, сохранён каждый исходный контракт, пройдены доступные mandatory checks и правдиво отражены ограничения. Публикация либо согласованное закрытие завершает вторую пару и всю заявку; до этого Execution остаётся in progress.
