# Анализ harness EPL для GLOBAL_HARNESS_ENVIRONMENT

Дата: 2026-10-04. Статус: первичный анализ; инвентаризация и поведенческая проверка не завершены.
Этот файл — отчёт и журнал согласования данной задачи, не действующая инструкция агента.

## Согласованные требования

- Пользователь выбрал вариант 1: создать результат в GLOBAL_HARNESS_ENVIRONMENT; `bts-transenergo-epl-server` — строго read only. Не изменять его файлы, Git-метаданные и runtime-кеши; не мигрировать. Все записи этой задачи — в новый проект или временные каталоги вне EPL.
- Разделить переносимые знания и специфичные знания EPL физически по разным папкам: `harness/common/` и `harness/project/`.
- Обе папки независимо переносимы и работоспособны. `common/` не требует `project/` и обязательных ссылок на EPL; `project/` имеет собственный индекс и необходимые проверки и не требует файлов, скиллов или скриптов из `common/`.
- Поддержать три режима: только common, только project, оба вместе. При совместном использовании знания дополняют друг друга; обнаруженные конфликты выносятся на согласование.
- Проверять каждую папку отдельно после копирования в чистый временный проект без соседней папки: ссылки, доступность процедур, работа проверок.
- Инструкции подключения читать при установке/диагностике; на старте только короткие обязательные ограничения и указатели; детали открывать по текущей задаче. Одинаковые знания между папками не дублировать.
- Комплектность файлов не означает загрузку всех файлов. Совокупный стартовый контекст двух папок отдельно ограничить и проверить; численный бюджет пока не согласован.
- Отдельно хранить базовые настройки/контракты, принятые решения, опыт ошибок, тестовую дисциплину и механическую защиту.
- При накоплении новых уроков агент предлагает сохранение; после подтверждения сохраняет контекст и требуемый результат. Обработка накопленного материала — в отдельной сессии по запросу пользователя.
- Все решения по вариантам и конфликтам согласовывать последовательно. После вопроса ждать ответа.
- Директива пользователя 2026-10-04: согласованные папки структуры harness создавать заранее, включая категории без рабочих материалов; в каждой папке — человеческое пояснение с понятным примером, исключённое из чтения агентами и их контекста. Прежнее предложение агента не создавать пустые категории отменено. Правило: harness/common/rules/human-folder-guides.md; охват проверки и ограничения: docs/analysis/human-folder-guides-validation.md.
- Выбор одинаковой либо различающейся системы категорий common/project ещё ожидает ответа; новая директива о человеческих пояснениях не считается этим выбором.
- Для новых правил и скиллов использовать skill-creator, superpowers:writing-skills, plugin-eval, evaluate-skill, evaluate-plugin и plugin-management в пределах их применимости. Согласование формата пакета и конкретных проверок впереди.

## Приёмка независимости — требования, ещё не выполненные проверки

| Режим | Условия проверки | Требуемый результат |
|---|---|---|
| Только common | В чистый временный проект скопирована только `harness/common/`; project отсутствует; исходный EPL не используется как зависимость | Собственный индекс работает, необходимые внутренние ссылки и ресурсы доступны, проверки запускаются; обязательных зависимостей на project/EPL нет |
| Только project | В другой чистый временный проект скопирована только `harness/project/`; common отсутствует | Собственный индекс работает, процедуры и проверки доступны без файлов, скиллов и скриптов common |
| Оба вместе | В третий временный проект скопированы обе папки | Обе доступны; обнаруженный конфликт не разрешается молча; совместная загрузка соблюдает отдельно согласованный стартовый бюджет |
| Нарушенная комплектность | В изолированной копии удалён обязательный локальный ресурс или повреждена ссылка | Соответствующая проверка замечает повреждение и даёт диагностируемый отказ; зелёный результат на пустой выборке не считается доказательством |

Приёмка должна отдельно показать комплектность, подключение к Codex/Claude и поведение. Проверка существования файлов не доказывает чтение агентом, а успешный запуск инструмента не доказывает обязательность его запуска.
Ссылки на источники происхождения опыта не должны становиться скрытыми обязательными зависимостями установленной папки. Возможности и ограничения живого проекта проверяются отдельно от автономной работоспособности пакета знаний; отсутствие приложения в чистом временном проекте нельзя выдавать за успешную проверку его поведения.
Существующие глобальные скиллы автора или соседние каталоги не должны маскировать неполноту тестовой копии.
Формат подключения, внешние prerequisites и точные бюджеты ещё предстоит согласовать. Здесь зафиксированы требования пользователя, а не выбранная реализация.

## Живой замер правил

Команда в EPL: `UV_CACHE_DIR=/tmp/global-harness-uv-cache uv run --no-sync python -m scripts.rules lint`.

Результат: 40 правил, 5 always-on; 0 error, 38 warn; код возврата 0.
Оценка инструмента: always-on около 28 720 токенов; сумма всех path-scoped около 305 147 токенов.
Это статическая оценка содержимого правил, не измеренные расходы запроса, не стоимость всех сессий и не утверждение, что все path-scoped правила грузятся вместе.
В неё не входит весь прочий контекст: AGENTS.md, скилловые описания, пользовательские инструкции и инструменты.
У console-ui.md, db.md и testing.md нулевой запас по строкам до местного жёсткого предела.

## Проверенные ограничения защиты

1. `tests/conftest.py::_block_real_network_hosts`: описание обещает дополнительную сетевую защиту, но реализация содержит только `yield None`. Эта фикстура сама не блокирует сеть. Это не доказывает отсутствие иных сетевых ограничений окружения.
2. `scripts/pytest_diff.py::select_tests`: удалённый тест отмечается в notes и не передаётся pytest; возможные импортёры выбираются отдельно. Эта ветка сама не сохраняет потерянный поведенческий контракт и не оценивает обоснованность удаления.
3. `.claude/hooks/inject-domain-rules.py`: всегда exit 0; выдаёт подсказку; основной проход рассматривает `.claude/rules/*.md`, а не вложенные правила. Это помощь маршрутизации, не блокирующий контроль чтения.
4. `.claude/settings.json` подключает такой хук к Write/Edit/MultiEdit. Из этого не следует защита произвольной записи через shell или работа этого хука в Codex.
5. `tests/scripts/test_guard_full_run_hook.py` явно проверяет, что канонический `pytest_diff --full` разрешён. Запрет полного прогона агентом частично остаётся процедурным: наличие команды не означает разрешение агенту её запустить.
6. `scripts/rules_kit.py::lint_rule` проверяет объём и распознаваемые ссылки, но не доказывает обязательность выполнения правил или их фактическую актуальность. Наличие `fails-when` в шаблоне не равно отдельной обязательной проверке каждого запрета.

Исходный код не исправлялся. Тесты не запускались; приведённые ограничения проверены чтением текущих реализаций. Их поведенческая проверка нового harness — будущая работа.

## Совместимость и переносимость

Официальная документация Claude Code на дату проверки описывает прямую загрузку AGENTS.md с v2.1.277, условия выбора между CLAUDE.md и AGENTS.md и дополнительные ограничения отдельных сессий до v2.1.281. `CLAUDE.md` с `@AGENTS.md` остаётся документированным способом совместимости; обычная просьба прочитать файл не эквивалентна импорту.
Источник: https://code.claude.com/docs/en/memory

Codex использует AGENTS.md и ограничивает суммарный размер проектных инструкций параметром project_doc_max_bytes (по умолчанию 32 KiB). Лимит — потолок совместимости, не целевой бюджет нового harness.
Источник: https://learn.chatgpt.com/docs/agent-configuration/agents-md

Автоматическое обнаружение скиллов зависит от стандартных каталогов конкретного агента. Простое помещение произвольной папки harness в проект не доказывает обнаружение её скиллов. Способ подключения нужно согласовать и проверить отдельно.

## Согласованное каноническое хранение

Проектный `octadim-create-always-loaded-claude-codex-rules` предписывает личную папку `.claude/rules/octadim/`, исключение её из Git через `.git/info/exclude`, запрет изменения AGENTS.md/CLAUDE.md и ручное подключение в настройках Codex. Это конкретный личный workflow источника; дословный перенос расходится с целью общей переносимой основы.

2026-10-04 пользователь выбрал вариант 1: канонические материалы хранить в Git проекта GLOBAL_HARNESS_ENVIRONMENT (session-settled: user-directed — chosen over Git-excluded storage: история изменений, сравнение и восстановление). Это согласованная замена личного workflow источника для создаваемого переносимого harness; исходный скилл EPL не меняется. Личные настройки и секреты не входят в переносимые материалы. Публикация и remote не согласованы и этим решением не создаются. Способ подключения к обоим агентам, категории файлов и проверки производных файлов выбираются отдельно.
